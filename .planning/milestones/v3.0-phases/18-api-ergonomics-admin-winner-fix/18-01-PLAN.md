<objective>
API-02: surface the already-stored bounty formula component breakdown on bounty and
leaderboard responses. The `bounty_points.inputs` jsonb is already computed upstream by the
statistics module — this plan ONLY reads it at the `mapBounty` mapper boundary and folds it
into an additive, optional `breakdown` aggregate. No formula change, no recomputation, no
new query.

Purpose: `web` needs explainable bounty (victim effectiveness, squad effectiveness, base
score, counted kills) per D-02. The breakdown is the trust surface for the bounty leaderboard.
Output: `BountySummaryResponse.breakdown` on both `/stats/bounty` and `/stats/leaderboards`.

CRITICAL prerequisite (carried from prior planning session): `listBounty`'s SELECT currently
OMITS the `bounty.inputs` column and `BountyRow` has no `inputs` field — both MUST be added
before `mapBounty` can fold the breakdown. This is Task 1.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-18-01 | Information Disclosure | mapBounty breakdown | mitigate | Aggregate-only output: emit countedKills/victimEffectiveness/squadEffectiveness/baseScore numbers; never emit victim_player_id/victim_squad_id from inputs.events (no ids leave the mapper) |
| T-18-02 | Denial of Service / Tampering | legacy/null/old-version inputs rows | mitigate | Defensive guard `inputs == null || inputs.version !== 1` → breakdown: null; single fold over events, no recursion, bounded by row's stored event count |
| T-18-03 | Information Disclosure | Steam64 in breakdown | mitigate | Breakdown carries only numbers + counts; covered by the leak-guard sweep extension in plan 18-04 (no Steam64 over /stats/bounty + /stats/leaderboards bodies) |
</threat_model>
