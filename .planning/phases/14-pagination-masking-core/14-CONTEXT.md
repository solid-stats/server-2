# Phase 14: Pagination & Masking Core - Context

**Gathered:** 2026-05-31
**Status:** Ready for planning

<domain>
## Phase Boundary

Every list endpoint (players, squads, bounty, leaderboards) moves to a single opaque-cursor + server-side-sort contract, and full Steam64 ids can never leave the server. This phase delivers the pagination/masking core that all later read surfaces build on: the cursor encode/decode primitive, the keyset SQL pattern with a guaranteed unique `id` tie-breaker, the masking enforcement at the row→payload mapper boundary, and rejection of mixed `page`/`cursor` requests. Requirements: PAGE-01, PAGE-02, PAGE-03, SEC-01, SEC-02.

</domain>

<decisions>
## Implementation Decisions

### Pagination Contract
- Replace `page`/`pageSize`/`total` on all list responses with an opaque cursor contract. The `total`, `page`, and `pageSize` fields must no longer appear on any list response.
- Response carries `items` + `nextCursor` (+ a boolean `hasMore`). No `total` and no count surface — clean keyset, no expensive COUNT, no approximate-total field. (User: "Без total".)
- A request that supplies both `page` and `cursor` is rejected (400) rather than silently resolved.

### Cursor Token
- Opaque cursor is `base64url` of a structured payload `{ sort, order, values[], id }` — **unsigned**. The cursor is not a secret; integrity is enforced by structural validation on decode (shape, sort/order against the endpoint whitelist, value types). Add zero new runtime dependencies. (User: "base64url без подписи".)
- Decode failures (malformed base64, wrong shape, sort/order not in the endpoint whitelist) are rejected as a 400 validation error, not silently ignored.

### Sort Contract
- Sorting expressed as two explicit query params: `?sort=<field>&order=asc|desc`. Each endpoint defines a whitelist of sortable fields and a default sort; unknown fields are rejected. (User: "sort=field&order=asc|desc".)
- Every sort tuple ends in a unique `id` tie-breaker so ordering is deterministic and stable across page boundaries — including rows that share a sort value and rows with NULL sort keys (explicit NULLS FIRST/LAST ordering folded into the keyset predicate).
- The cursor's encoded `sort`/`order` must match the request's `sort`/`order`; a mismatch is rejected (prevents resuming a cursor under a different ordering).

### SteamID Masking (SEC-01 / SEC-02)
- SteamID identity is surfaced only as a **masked last-4 form** (e.g. `...7890`), never the full Steam64. (User: "Masked last-4".)
- Masking is enforced server-side at the row→payload mapper boundary (the single choke point), so no payload, cursor token, log line, or error path can emit a full Steam64.
- Acceptance: a `7656119\d{10}` regex over any public response body, cursor token, log line, and error payload finds zero matches.

### Claude's Discretion
- Exact field naming for the masked value (e.g. `steamIdMasked` vs reusing `steamIds` as masked strings) — choose the least surprising shape for `web` and keep it consistent across endpoints; document in the plan.
- Internal module layout for the cursor codec and keyset query builder.
- Whether `hasMore` is derived by fetching `limit + 1` rows or by cursor presence — pick the standard keyset approach.

</decisions>

### Established Patterns
- DB layer is raw `pg` Pool (`src/infra/db/client.ts:6-9`), parameterized SQL strings (`$1`, `$2`), no ORM/query builder — keyset predicates must be built as parameterized SQL.
- Route schemas are TypeBox via `@fastify/type-provider-typebox`; OpenAPI auto-generated by `@fastify/swagger` from registered schemas (`src/openapi/register-openapi.ts`). Schema edits regenerate the contract on boot.
- List endpoints live in `src/modules/public-stats/routes.ts`: players (131-145), squads (176-190), bounty (232-246), leaderboards (248+, non-paginated array).

### Integration Points
- SteamID leak to close: `PlayerProfileResponse.steamIds` (`schemas.ts:60-66`), emitted by `mapPlayerProfile()` (`repository.ts:517-526`) from the `coalesce(array_agg(... steam_id ...))` fetch (`repository.ts:208`). Masking enforced here.
- No shared validation-error helper exists for the mixed `page`/`cursor` rejection — add explicit validation in the cursor/filter layer or a pre-handler.
- Leaderboards currently return a non-paginated array — confirm during planning whether it joins the cursor contract or is explicitly exempt.

<specifics>
## Specific Ideas

- Masked form is last-4 digits with a leading ellipsis marker (e.g. `...7890`); keep it a string so `web` renders it directly.
- Zero new runtime dependencies — cursor codec uses Node's built-in base64url; this is a product-wide constraint (STATE.md decision).

</specifics>

<deferred>
## Deferred Ideas

- Approximate/exact total endpoints — explicitly rejected for this milestone (no count surface).
- HMAC-signed or encrypted cursors — not needed since the cursor carries no secret; revisit only if cursor tampering becomes an attack concern.

</deferred>
