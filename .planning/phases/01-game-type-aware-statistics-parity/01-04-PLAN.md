<objective>
Make the legacy export path emit per-type + all-time aggregates and the is_show split, matching what the
parity-driver diffs against. Update `parity-sql.ts` (`playerStatsSql`/`squadStatsSql`) and
`legacy-export.ts` (`ROTATION_STATS_SQL`, the global player/squad selects) so they read the correct
`game_type` / all-time (rotation_id NULL) rows instead of summing the type-agnostic bulk, and surface
`is_show` from `player_stats` so the export reproduces the `otherPlayers` / main-player split by a straight
read (D3). Keep the public HTTP API / OpenAPI contract byte-unchanged (parity-first).

Purpose: 01-03 produced the game-type-aware rows; this plan makes the legacy export *consume* them in the
shape legacy `sg_stats` produces, which is what F8 parity compares. The export contract already supports
`isShow` (LegacyPlayerStatsInput.isShow optional; playerExport uses `input.isShow ?? true`), so this is a
data-sourcing change, not a contract change.
Output: Per-type/all-time-aware parity SQL + legacy-export SQL with is_show passthrough, plus updated unit +
real-pg export tests.
</objective>

    `playerStatsSql`/`squadStatsSql` currently `left join player_stats stats on stats.player_id = player.id`

    selection so it reads exactly one bucket per type:
    - The global player/squad totals must come from the all-time rows (`rotation_id is null`) per game_type,
      NOT a sum over per-rotation + all-time (which would double-count). Add a `game_type` dimension to the
      scoping: the parity SQL builders take (or are duplicated per) game_type, selecting
      `where stats.rotation_id is null and stats.game_type = $gameType`.
    - Add `is_show` to the player select (`stats.is_show`) so it can flow to the export. Since global player
      stats are the all-time bucket, is_show comes from the all-time player_stats row for that type.
    - Preserve the existing per-entity `scope` (scopeId) parameter and ordering exactly (kills desc, name,
      id) — the parity-driver depends on stable ordering; only the row *source* changes (all-time + type),
      not the projection columns or sort.

    the `rotation_id is null and game_type = ...` predicate are present in the generated SQL for each type.
    Keep `PLAYER_ENTITY_CTE`-derived weapons/weeks/relationships unchanged (they aggregate events, which are
    not game-type-bucketed in legacy global counters — confirm against RESEARCH; if legacy scopes weapons/
    weeks per type too, surface it, but default: leave event-derived surfaces as-is since they read
    parser_events not player_stats).
