# Quick Task 260614-c0d: Fix F7 — set-based recalculation so the parity check can pass

## Problem (root cause)

`FullRunRecalculationService.recalculateAllCurrentParserResults` iterates **per
parser_result** (per replay). Each `recalculate*ForParserResult` call rebuilds the
**entire rotation's** aggregates from scratch (`loadAggregateReplayInputs` filters by
`rotation_id`, then `replaceAggregateRows` deletes+reinserts the whole rotation). A
rotation of size *m* is therefore fully rebuilt *m* times → **O(m²) per rotation,
O(n²) corpus-wide**, DB-bound. Measured ~2 replays/min, ETA ~5 days for 23.5k
(parity F7, 🔴). R11 (3710 replays) dominates.

## Key correctness insight

The per-parser-result recalc methods are **already full-rotation rebuilds** — they do
not accumulate incrementally. So rebuilding each rotation **once** (after every replay
in it is assigned to its rotation) yields **byte-identical aggregates** to the
per-replay path, at O(n). Bounty reads the *previous* rotation's `player_stats`, so
rotations must be rebuilt in chronological order (targets are already ordered by
`replay_timestamp`, so first-seen rotation order is chronological).

## Approach

Set-based, two phases, no change to the single-replay audit path
(`recalculate*ForParserResult` stay untouched — still used by
`audit-recalculator` / `workflow-applier`):

1. **Batch rotation assignment** — one set-based `UPDATE replays … FROM rotations`
   over all current-result replays, returning a `replayId → rotationId` map.
2. **Rebuild each rotation once** — group resolved targets by rotation in target
   order, call new `recalculate*ForRotation(rotationId)` repo methods once per
   rotation (player/squad → commander → bounty).
