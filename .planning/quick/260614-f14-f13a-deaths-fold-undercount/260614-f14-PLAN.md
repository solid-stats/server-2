# Quick Task 260614-f14: Fix the F13a deaths-fold undercount

## Problem (root cause)

After F12 + F13a + a full recalc, `sg` `deaths.total` runs ~5% **below** legacy,
while games/kills are within ~1.5%. The decisive evidence is per-player: the
recalc's `deaths.total` is 3-6% lower than the parser's own death-game signal
(replays where the player's `player_counter.deaths_total > 0`, i.e. parser
`player.d > 0`), which itself matches legacy. So the parser is right; the loss is
in server-2's death **aggregation** (`calculatePlayerAndSquadAggregates`,
`src/modules/statistics/service/service.ts`).

The leak is the interaction between the F13a per-replay cap and the **pre-F13a
`counterDeathReferences` suppression**, which F13a left in place:

- `counterDeathReferences` (was `service.ts` ~88-95) is a `Set` of
  `event.observedPlayerRef` for **every** `player_counter` whose
  `counterDeaths(payload) !== undefined`. Note `counterDeaths` returns a DEFINED
  `{total:0,…}` even for an explicit-zero counter (`deaths_total:0`); it is
  `undefined` only when both `deaths_total` and `deaths_by_teamkills` are absent.
- `applyVictimDeath` / `applySquadEvent` (victim branch) SUPPRESSED the victim
  kill-row death when `counterDeathReferences.has(String(victim_entity_id))`.
- `applyCounterEvent` resolves `playersByEntity.get(event.observedPlayerRef)` and
  RETURNS EARLY (drops the death) when the player is unresolved.

**The leak:** when an entity has a `player_counter` in `counterDeathReferences`
(so the victim path is suppressed for that entity) but the counter path records
nothing for the resolved victim — because the counter reports an explicit-zero
`deaths_total` (`incrementDeathsByCounter` adds 0), or because `observedPlayerRef`
does not resolve in `playersByEntity` — the real victim kill-row death is lost
from **both** paths. The two paths also key differently (counter on
`observedPlayerRef`, victim on `String(victim_entity_id)`), so any resolution
mismatch between them leaks a death.

Reproduced as a failing unit test before the fix: a replay with a
`player_counter` `deaths_total:0` for entity 202 plus a `kill` row whose victim is
202 (resolving to player-b) yields `deaths.total: 0`, where the target invariant
requires `1`.

## Target invariant

Per canonical player, all-time `deaths.total` MUST equal the number of distinct
replays in which that player died at least once (one-life: capped at 1/replay) —
equivalently the parser's `d>0` replay count.

## Approach

With F13a's per-replay cap (`foldCappedDeaths` caps to <=1 `total` and <=1
`by_teamkills` per replay) already in place, the `counterDeathReferences`
suppression is **redundant and harmful**: double-counting between the counter path
and the victim path now just collapses to 1 per replay anyway. The minimal fix is
to **stop suppressing the victim path** and let both paths tally into the
per-replay scratch maps; whichever path resolves the entity records the (capped)
death.

- Remove `counterDeathReferences` (construction, the `ReplayEventContext` field,
  and both `.has(...)` suppression checks in `applyVictimDeath` and
  `applySquadEvent`).
- Both the counter path and the victim kill-row path now write into
  `replayPlayerDeaths` / `replaySquadDeaths`; `foldCappedDeaths` collapses any
  double-count to a single death and keeps `by_teamkills <= total`.

This stays entirely in the **service** layer (the aggregation owner) — no parser,
schema, repository SQL, or API-contract change
(`solidstats-server-ts-conventions` §A: keep each layer doing its own job). F13a's
cap is preserved: a player with `d=3` in one replay still counts 1.
