# Full-Run Recalculation

This document defines the Phase 10 operator surface for recalculating current parser results and reporting coverage/freshness evidence.

## Commands

Dry-run coverage report:

```bash
pnpm run ops:stats:coverage
```

Full recalculation:

```bash
pnpm run ops:stats:recalculate
```

Both commands read the standard app database configuration, connect to PostgreSQL, print JSON to stdout, and leave runtime orchestration to the operator or infrastructure workflow.

## Dry-Run Coverage Report

`pnpm run ops:stats:coverage` does not mutate aggregate tables. It reports:

- lifecycle counts for staging records, replays, parse jobs, and parser results;
- current parser result targets in deterministic replay timestamp / creation order;
- freshness status for each current parser result;
- conservative identity-gap status for parser players with blank observed names.

The top-level report fields are:

| Field           | Meaning                                            |
| --------------- | -------------------------------------------------- |
| `reportVersion` | Report contract version.                           |
| `mode`          | `coverage` for dry-run coverage output.            |
| `generatedAt`   | ISO timestamp generated by the command process.    |
| `lifecycle`     | Status counts for staging, replays, jobs, output.  |
| `summary`       | Current parser result, stale, and identity counts. |
| `targets`       | Per-current-parser-result coverage evidence.       |

## Recalculation Report

`pnpm run ops:stats:recalculate` recalculates all current parser results through the same aggregate replacement paths used by parser completion and approved audit corrections.

The command is idempotent at the aggregate-table level because player, squad, commander-side, and bounty rows are replaced for the affected rotation.

The `summary` object includes:

| Field                         | Meaning                                                       |
| ----------------------------- | ------------------------------------------------------------- |
| `parserResultCount`           | Current parser results considered by the command.             |
| `recalculatedCount`           | Parser results that completed aggregate recalculation.        |
| `skippedCount`                | Parser results skipped for known input readiness reasons.     |
| `failureCount`                | Parser results that threw unexpected recalculation errors.    |
| `missingRotationCount`        | Skips caused by replay timestamps outside known rotations.    |
| `missingReplayTimestampCount` | Skips caused by replays without replay timestamps.            |
| `missingIdentityCount`        | Parser results with conservative blank-name identity gaps.    |
| `staleCount`                  | Current parser results whose aggregate freshness is unproven. |
| `changedAggregateRows`        | Aggregate rows written by successful recalculation outcomes.  |

Each `results[]` item includes replay identifiers and enough evidence to retry or fix inputs:

- `parserResultId`
- `replayId`
- `sourceSystem`
- `sourceReplayId`
- `replayTimestamp`
- `rotationId`
- `status`
- `reasonCode` for skipped or failed items
- `errorMessage` for failed items
- `aggregateRows` for recalculated items

## Reason Codes

| Reason code                | Meaning                                                        |
| -------------------------- | -------------------------------------------------------------- |
| `missing_replay_timestamp` | The replay has no timestamp, so no rotation can be assigned.   |
| `missing_rotation`         | The replay timestamp does not map to a known rotation.         |
| `missing_identity`         | The parser result has at least one blank observed player name. |
| `recalculation_failed`     | Recalculation threw an unexpected error.                       |

## Lifecycle Counts

The `lifecycle` object separates supported operational states without ad hoc SQL:

- `staging`: `pending`, `processing`, `promoted`, `conflicted`, `failed`, `ignored`
- `replays`: `staged`, `ready_for_parse`, `parsed`, `parse_failed`, `archived`
- `parseJobs`: `queued`, `published`, `running`, `succeeded`, `failed`, `retryable`
- `parserResults`: `current`, `superseded`, `failed`

Unknown future states are preserved in the relevant count object instead of being dropped.

## Freshness Semantics

A current parser result is reported as stale when aggregate freshness cannot be proven from current `calculated_at` timestamps for player, squad, commander-side, and bounty aggregate tables.

Freshness is evidence for operator review. It does not replace the full recalculation command.

## Identity Boundary

Phase 10 reports identity gaps conservatively. `missingIdentityCount` currently means at least one parser player has a blank observed name in the current parser result.

Phase 11 owns deeper rotation and no-SteamID readiness:

- nickname history import/export;
- validity-window conflict reporting;
- unresolved observed nickname reporting;
- future SteamID migration behavior for historical no-SteamID data.

## Boundaries

These commands do not:

- fetch or parse OCAP replay files;
- crawl replay sources;
- mutate Kubernetes, Compose, SSH, or deployment state;
- capture legacy `sg_stats` snapshots;
- store full-run evidence artifacts outside stdout.

Infrastructure or operator workflows should archive stdout for sample, partial staging, and final full-corpus runs.
